# GraphCheck CI/CD guide

This guide shows four complete GitHub Actions patterns using the published
`graphora/graphcheck-action@v1`: a pull-request gate, a scheduled audit, a staging gate, and a
production audit. Each workflow keeps credentials in GitHub Secrets, publishes the GraphCheck
artifacts, and applies an explicit exit-code policy.

## Before you start

Commit `graphcheck.yml`, your `checks/` directory, and a secret-free `profiles.yml`. The profile
file contains connection metadata and the name of the password environment variable, never the
password itself:

```yaml
default: pr
profiles:
  pr:
    uri: neo4j+s://pr-graph.example.com
    user: graphcheck_pr
    password_env: NEO4J_PASSWORD
    database: neo4j
  scheduled:
    uri: neo4j+s://audit-graph.example.com
    user: graphcheck_scheduled
    password_env: NEO4J_PASSWORD
    database: neo4j
  staging:
    uri: neo4j+s://staging-graph.example.com
    user: graphcheck_staging
    password_env: NEO4J_PASSWORD
    database: neo4j
  production:
    uri: neo4j+s://production-graph.example.com
    user: graphcheck_prod_reader
    password_env: NEO4J_PASSWORD
    database: neo4j
```

If `graphcheck init` added `profiles.yml` to `.gitignore`, remove that ignore entry only after
confirming the file has no literal password. Add the corresponding passwords as GitHub Actions
secrets, such as `NEO4J_PR_PASSWORD`, `NEO4J_SCHEDULED_PASSWORD`,
`NEO4J_STAGING_PASSWORD`, and `NEO4J_PRODUCTION_PASSWORD`. Each workflow maps its secret to the
`NEO4J_PASSWORD` name referenced by `password_env`.

The published Action still requires `uri` and `user` inputs. When `profiles.yml` exists, it uses
the selected profile as-is; keep those inputs equal to the profile so the workflow remains correct
if the profile file is later generated by the Action instead.

The target must be reachable from the runner. Use a self-hosted runner or appropriate network
routing when a staging or production database is private. GitHub does not expose repository
secrets to workflows from untrusted forked pull requests; do not switch to `pull_request_target`
to run untrusted PR code with database credentials.

## Artifacts and exit codes

With the default `graphcheck.yml`, every run writes:

```text
.graphcheck/runs/latest/results.json
.graphcheck/runs/latest/summary.json
.graphcheck/runs/latest/report.html
```

`results.json` is the machine-readable result and stores the process code at `.run.exit_code`,
`summary.json` is the compact run-history record, and `report.html` is a self-contained offline
report. The Action's `upload-artifacts` input accepts `always`, `on-failure`, or `never`; uploaded
files appear in the workflow run as the `graphcheck-results` artifact.

GraphCheck's exit-code contract is:

| Code | Meaning | Typical policy |
| --- | --- | --- |
| `0` | The run completed, at least one check was evaluated, and every evaluated check passed. | Pass. |
| `1` | An error-severity check failed or errored. This takes precedence over an otherwise partial run. | Block the gate. |
| `2` | The run has warning-severity findings/errors, incomplete coverage, a partial run, or no evaluated checks. | Warn or block, according to the environment. |
| `3` | GraphCheck could not prepare or execute the run, for example because configuration, connectivity, or credential verification failed. | Block the gate and investigate. |

Without `continue-on-error`, the Action preserves the GraphCheck code and every nonzero code fails
the job after annotations, the Step Summary, and configured artifact upload have run. The examples
below use `continue-on-error: true`, read the exact code from `results.json`, and then apply a
named policy. If no valid result exists, the read step fails closed to code `3`.

## 1. Pull-request gate

This policy blocks error-severity failures (`1`) and infrastructure/setup failures (`3`), while
allowing warning or incomplete code `2` to remain visible without blocking the PR. The Action emits
GitHub error/warning annotations before the gate runs. An annotation points to the check YAML file
and line when available; otherwise it identifies the suite/check and finding in the PR checks UI.

The `pr` profile uses `password_env: NEO4J_PASSWORD`; the workflow supplies it from
`NEO4J_PR_PASSWORD`.

```yaml
name: GraphCheck PR gate

on:
  pull_request:

permissions:
  contents: read

jobs:
  graphcheck:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Run GraphCheck
        id: graphcheck
        continue-on-error: true
        uses: graphora/graphcheck-action@v1
        with:
          profile: pr
          uri: neo4j+s://pr-graph.example.com
          user: graphcheck_pr
          database: neo4j
          upload-artifacts: on-failure
        env:
          NEO4J_PASSWORD: ${{ secrets.NEO4J_PR_PASSWORD }}

      - name: Read GraphCheck exit code
        id: graphcheck_result
        if: always()
        shell: bash
        run: |
          result=.graphcheck/runs/latest/results.json
          code=3
          if [ -f "$result" ]; then
            code="$(jq -r '.run.exit_code // 3' "$result" 2>/dev/null || echo 3)"
          fi
          case "$code" in 0|1|2|3) ;; *) code=3 ;; esac
          echo "code=$code" >> "$GITHUB_OUTPUT"
          echo "GraphCheck exit code: $code"

      - name: Gate error-severity findings
        if: always()
        shell: bash
        env:
          GRAPHCHECK_EXIT_CODE: ${{ steps.graphcheck_result.outputs.code }}
        run: |
          case "$GRAPHCHECK_EXIT_CODE" in
            0|2) exit 0 ;;
            1|3) exit "$GRAPHCHECK_EXIT_CODE" ;;
            *) exit 3 ;;
          esac
```

For a strict PR gate, replace the final `case` with
`exit "${GRAPHCHECK_EXIT_CODE:-3}"`; that also blocks code `2`.

## 2. Scheduled run with alerting

This workflow runs every night, always uploads `results.json`, `summary.json`, and `report.html`,
opens a GitHub issue when GraphCheck returns a nonzero code, and then preserves that code as the job
failure. Swap the issue step for your Slack, PagerDuty, email, or incident-management Action if
needed.

The `scheduled` profile uses `password_env: NEO4J_PASSWORD`; the workflow supplies it from
`NEO4J_SCHEDULED_PASSWORD`.

```yaml
name: Scheduled GraphCheck audit

on:
  schedule:
    - cron: '17 3 * * *'
  workflow_dispatch:

permissions:
  contents: read
  issues: write

jobs:
  graphcheck:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Run GraphCheck
        id: graphcheck
        continue-on-error: true
        uses: graphora/graphcheck-action@v1
        with:
          profile: scheduled
          uri: neo4j+s://audit-graph.example.com
          user: graphcheck_scheduled
          database: neo4j
          upload-artifacts: always
        env:
          NEO4J_PASSWORD: ${{ secrets.NEO4J_SCHEDULED_PASSWORD }}

      - name: Read GraphCheck exit code
        id: graphcheck_result
        if: always()
        shell: bash
        run: |
          result=.graphcheck/runs/latest/results.json
          code=3
          if [ -f "$result" ]; then
            code="$(jq -r '.run.exit_code // 3' "$result" 2>/dev/null || echo 3)"
          fi
          case "$code" in 0|1|2|3) ;; *) code=3 ;; esac
          echo "code=$code" >> "$GITHUB_OUTPUT"
          echo "GraphCheck exit code: $code"

      - name: Open failure alert
        if: always() && steps.graphcheck_result.outputs.code != '0'
        uses: actions/github-script@v7
        env:
          GRAPHCHECK_EXIT_CODE: ${{ steps.graphcheck_result.outputs.code }}
        with:
          script: |
            const runUrl = `${context.serverUrl}/${context.repo.owner}/${context.repo.repo}/actions/runs/${context.runId}`;
            await github.rest.issues.create({
              ...context.repo,
              title: `Scheduled GraphCheck audit failed (exit ${process.env.GRAPHCHECK_EXIT_CODE})`,
              body: `GraphCheck returned exit code ${process.env.GRAPHCHECK_EXIT_CODE}. Review the annotations and graphcheck-results artifact: ${runUrl}`,
              labels: ['graphcheck']
            });

      - name: Preserve GraphCheck status
        if: always()
        shell: bash
        env:
          GRAPHCHECK_EXIT_CODE: ${{ steps.graphcheck_result.outputs.code }}
        run: exit "${GRAPHCHECK_EXIT_CODE:-3}"
```

Create the `graphcheck` label first or remove the `labels` field from the alert step.

## 3. Staging on merge

A `push` workflow on a protected `staging` branch runs after a pull request is merged into that
branch. Protect the branch against direct pushes if the workflow must run only for merges. This
example treats every nonzero code as a failed staging gate and always retains artifacts.

The `staging` profile uses `password_env: NEO4J_PASSWORD`; the workflow supplies it from the
`staging` GitHub Environment secret `NEO4J_STAGING_PASSWORD`.

## 4. Production read-only audit

Production must use defense in depth. On Neo4j Enterprise or Developer Edition, create a dedicated
account with only Neo4j's built-in `reader` role and the automatic `PUBLIC` role. Revoke `admin`,
`architect`, `publisher`, `editor`, and every custom role. Store its password only in the protected
`production` GitHub Environment as `NEO4J_PRODUCTION_PASSWORD`.

An administrator can grant and verify the role assignment with:

```cypher
GRANT ROLE reader TO graphcheck_prod_reader;

SHOW USERS
YIELD user, roles
WHERE user = 'graphcheck_prod_reader'
RETURN user, roles;
```

GraphCheck's run preflight checks the current Enterprise user's roles and fails closed if the
credential is not server-enforced read-only or its roles cannot be verified. Independently, every
customer-authored competency query is planned with `EXPLAIN`; GraphCheck executes it only when
Neo4j classifies it as a read query. The `EXPLAIN` guard is defense in depth, not a substitute for
the production credential's server-side authorization. Neo4j Community cannot provide that
server-enforced boundary and is therefore not recommended for this production pattern.

This example runs on a weekly schedule and whenever a GitHub release is published. It serializes
production audits, always uploads artifacts, and blocks every nonzero result.

```yaml
name: GraphCheck production audit

on:
  schedule:
    - cron: '29 4 * * 1'
  release:
    types: [published]
  workflow_dispatch:

permissions:
  contents: read

concurrency:
  group: graphcheck-production
  cancel-in-progress: false

jobs:
  graphcheck:
    runs-on: ubuntu-latest
    environment: production
    steps:
      - uses: actions/checkout@v4

      - name: Run GraphCheck
        id: graphcheck
        continue-on-error: true
        uses: graphora/graphcheck-action@v1
        with:
          profile: production
          uri: neo4j+s://production-graph.example.com
          user: graphcheck_prod_reader
          database: neo4j
          concurrency: 1
          upload-artifacts: always
        env:
          NEO4J_PASSWORD: ${{ secrets.NEO4J_PRODUCTION_PASSWORD }}

      - name: Read GraphCheck exit code
        id: graphcheck_result
        if: always()
        shell: bash
        run: |
          result=.graphcheck/runs/latest/results.json
          code=3
          if [ -f "$result" ]; then
            code="$(jq -r '.run.exit_code // 3' "$result" 2>/dev/null || echo 3)"
          fi
          case "$code" in 0|1|2|3) ;; *) code=3 ;; esac
          echo "code=$code" >> "$GITHUB_OUTPUT"
          echo "GraphCheck exit code: $code"

      - name: Gate production
        if: always()
        shell: bash
        env:
          GRAPHCHECK_EXIT_CODE: ${{ steps.graphcheck_result.outputs.code }}
        run: exit "${GRAPHCHECK_EXIT_CODE:-3}"
```

For production, keep `concurrency: 1` unless the database owner has approved a higher query load.
Use GitHub Environment reviewers to require approval for release-triggered access if your change
process requires it.

## Reading a completed run

Open the workflow's Step Summary for totals and the PR checks UI for inline annotations. Download
the `graphcheck-results` artifact for the full result, compact summary, and offline HTML report.
Locally, inspect the exact outcome with:

```console
jq '.run.exit_code, .run.status, .totals' .graphcheck/runs/latest/results.json
```

See the [`results.json` specification](specs/SPEC-01-results-json.md) for the complete result shape
and the [Action reference](ci-setup.md) for all inputs and execution details.
